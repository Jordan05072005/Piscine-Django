Partie 1 · Les bases de données

SQL vs NoSQL

SQL désigne les bases relationnelles : les données sont rangées dans des tables reliées entre elles, et on les interroge avec le langage SQL. Exemples : PostgreSQL, MySQL, SQLite, Oracle.

NoSQL (Not only SQL) regroupe toutes les autres familles. Elles ne forment pas un seul type : une base de documents, une base clé-valeur et une base de graphes n'ont presque rien en commun, à part le fait de ne pas être relationnelles. Exemples : MongoDB, Redis, Cassandra, Neo4j.

SQLNoSQL
ModèleTables, lignes et colonnesSelon la famille : documents, clé-valeur, colonnes larges, graphes...
StructureSchéma fixe, imposé par la baseSchéma souple, souvent imposé seulement par l'application
LangageSQL, standardisé et commun à toutes les basesPropre à chaque base : requêtes MongoDB, commandes Redis, Cypher...
RelationsAu cœur du modèle : clés étrangères et jointuresPeu ou pas de jointures : on regroupe ou on duplique
TransactionsGaranties ACID complètesVariables, souvent une cohérence à terme
Montée en chargeSurtout verticaleSouvent horizontale

La frontière est de plus en plus floue : PostgreSQL sait stocker et interroger du JSON avec le type JSONB, MongoDB propose des transactions sur plusieurs documents, et certaines bases distribuées gardent le langage SQL.

Forces et inconvénients

Forces

  • Cohérence stricte : la base refuse les données invalides
  • Transactions ACID fiables, idéales pour l'argent et les stocks
  • Requêtes puissantes : jointures, agrégations, statistiques
  • Langage standard, connu partout, écosystème très mûr
  • Chaque information n'est stockée qu'une fois

Inconvénients

  • Structure rigide : chaque changement demande une migration
  • Montée en charge horizontale plus complexe
  • Jointures coûteuses sur de très gros volumes
  • Peu adapté aux données de forme variable
  • Données hiérarchiques ou imbriquées moins naturelles

Forces

  • Structure souple : un champ s'ajoute sans migration
  • Montée en charge horizontale souvent prévue dès la conception
  • Très rapides pour leur usage cible : document complet, accès par clé...
  • Modèles adaptés à des besoins précis : cache, graphe, séries temporelles
  • Pratiques pour prototyper quand le modèle bouge encore

Inconvénients

  • La cohérence repose davantage sur le code de l'application
  • Jointures absentes ou limitées : duplication ou requêtes multiples
  • Transactions plus limitées, ou cohérence seulement à terme
  • Pas de langage commun : chaque base a sa syntaxe
  • Les données dupliquées doivent être mises à jour partout

Les autres types de bases

« NoSQL » recouvre plusieurs familles, chacune pensée pour un besoin précis. D'autres types gardent le SQL tout en visant des usages particuliers.

En pratique, on les combine. Une application courante utilise souvent PostgreSQL comme source de vérité, Redis comme cache et Elasticsearch pour la recherche : c'est la persistance polyglotte.

Partie 2 · Les outils pour les manipuler

ORM vs ODM

Un ORM et un ODM permettent de manipuler la base avec des objets de ton langage plutôt qu'en écrivant des requêtes. Ils ont le même rôle : seule la base qu'ils traduisent change.

ORMODM
Nom completObject-Relational MappingObject-Document Mapping
Base viséeRelationnelle (SQL)Orientée documents (MongoDB)
Une classe ↔une tableune collection
Un objet ↔une ligneun document
ExemplesDjango ORM, TypeORM, Prisma, SQLAlchemyMongoose

Le trajet d'une opération

  1. Ton codeLivre.objects.filter(annee=2020)
  2. ORMTraduit l'appel en requête SQL
  3. Requête SQLSELECT * FROM livre WHERE annee = 2020;
  4. Base relationnelleRenvoie des lignes, que l'ORM convertit en objets
  1. Ton codelivreModel.find({ annee: 2020 })
  2. ODM (Mongoose)Valide avec le schéma, puis traduit en requête MongoDB
  3. Requête MongoDBdb.livres.find({ annee: 2020 })
  4. MongoDBRenvoie des documents, que l'ODM convertit en objets

Ce qu'ils ont en commun

  • Des objets au lieu de requêtes : l'outil génère la requête adaptée à la base.
  • Une description des données dans le code : un modèle, une entité ou un schéma.
  • De la validation : types et champs obligatoires vérifiés avant l'écriture.
  • De la sécurité : les valeurs sont échappées, ce qui protège des injections.

Ce qui les différencie

ORM (base SQL)ODM (MongoDB)
Qui impose la structure ?La base : une colonne manquante provoque une erreurL'application : c'est le schéma de l'ODM qui impose une forme
RelationsClés étrangères et jointuresDocuments imbriqués, ou références avec populate()
Changer la structureMigrations obligatoiresEn général pas de migration
TransactionsNatives et centralesPossibles, avec plus de contraintes
Point fortDonnées très liées, cohérence stricteForme variable, lecture d'un bloc complet

Exemple : un auteur et ses livres

Deux tables reliées par la clé étrangère auteur_id. Pour obtenir un auteur avec ses livres, il faut une jointure.

class Auteur(models.Model):
    nom = models.CharField(max_length=100)

class Livre(models.Model):
    titre = models.CharField(max_length=100)
    annee = models.IntegerField()
    auteur = models.ForeignKey(Auteur, on_delete=models.CASCADE, related_name="livres")

Django inclut son propre ORM : ces classes suffisent pour créer les deux tables avec makemigrations et migrate.

@Entity()
export class Auteur {
  @PrimaryGeneratedColumn() id: number;
  @Column() nom: string;
  @OneToMany(() => Livre, (livre) => livre.auteur) livres: Livre[];
}

@Entity()
export class Livre {
  @PrimaryGeneratedColumn() id: number;
  @Column() titre: string;
  @Column() annee: number;
  @ManyToOne(() => Auteur, (auteur) => auteur.livres) auteur: Auteur;
}

NestJS n'a pas d'ORM intégré : on lui branche TypeORM, et chaque classe @Entity() devient une table.

Un seul document contient l'auteur et ses livres : une seule lecture suffit, sans jointure. En contrepartie, un livre partagé entre plusieurs documents doit être dupliqué, ou rangé à part avec une référence.

@Schema()
export class Livre {
  @Prop() titre: string;
  @Prop() annee: number;
}
export const LivreSchema = SchemaFactory.createForClass(Livre);

@Schema()
export class Auteur {
  @Prop() nom: string;
  @Prop({ type: [LivreSchema] }) livres: Livre[];
}
export const AuteurSchema = SchemaFactory.createForClass(Auteur);

Le schéma décrit la forme des documents. C'est le modèle créé par Mongoose à partir de ce schéma qui fournit find, create...

Prisma et MikroORM savent parler aux deux familles. Et un framework n'est ni l'un ni l'autre : Django inclut son ORM, NestJS n'en inclut aucun.

Les pièges à connaître

ORM : les requêtes N+1 
for livre in Livre.objects.all():   # 1 requête
    print(livre.auteur.nom)         # + 1 requête par livre
Avec 100 livres, 101 requêtes. La solution : Livre.objects.select_related("auteur"), une seule requête avec jointure.
ODM : la structure qui dérive
La base n'impose rien : d'anciens documents peuvent garder une ancienne forme. Le code doit gérer ces cas, ou un script doit les mettre à jour.
Des deux côtés : oublier que la requête existe
L'outil masque les requêtes sans les rendre gratuites. Vérifie ce qui part vraiment à la base : print(queryset.query) en Django, logging: true avec TypeORM.

Choisir entre les deux

On ne choisit pas l'outil en premier, mais la base : l'outil en découle.

Base SQL + ORM si...

  • les données sont très liées : utilisateurs, commandes, factures
  • la cohérence est critique : argent, stocks, réservations
  • tu as besoin de requêtes croisées et de statistiques

MongoDB + ODM si...

  • la forme des données varie d'un élément à l'autre
  • tu lis surtout des blocs complets d'un coup
  • la structure évolue souvent, sans migrations

En cas de doute, une base SQL est le choix par défaut le plus sûr. C'est aussi celui de Django, dont l'ORM ne gère que des bases relationnelles.
